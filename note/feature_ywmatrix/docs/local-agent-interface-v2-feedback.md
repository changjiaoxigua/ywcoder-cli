## ① `decision: "cancel"` 的语义与我方实现相反（✅ 已确认采用方案 A）

> **结论（2026-08-11）**：贵方确认采用**方案 A**——`cancel` = 中止整个任务，效果等同 §6.3 `task.cancel`；前端「×」/「关闭」按钮映射为 `deny`，只有明确的「终止任务」按钮才发 `cancel`。我方实现即为此，代码零改动。**请按下文措辞更新 v2 §6.2.1 的表格**。
>
> 补充一条我方的旧版兼容处理：v2 §6.2.1 允许收到自由字符串，此时**裸的「取消」/`cancel` 字符串我方仍按 `deny` 处理**（这类客户端尚未遵循上述前端约定，其「取消」多半是「别做这个操作」，不应据此杀掉整轮任务）。结构化 `{decision:'cancel'}` 不受此限。

以下为原始问题描述，存档备查。


**v2 现状**（§6.2.1）：

> | `cancel` | 用户主动取消整个确认（区别于 §6.3 停止任务） |

**我方实现**：`cancel` → 向 ywcoder 回 `{behavior:"deny", message, interrupt:true}` → **整轮任务立即中止**，返回 `event.error`（`error_during_execution`）。已端到端实测。

两边正好相反：文档说「不是停止任务」，实现是「就是停止任务」。

**风险**：如果前端把「点弹窗右上角 ×」映射成 `cancel`，用户随手关一个确认框 = 整个任务被中止。这个误操作代价很高（长任务前功尽弃）。

**根因**：被控端 ywcoder 对一次权限请求只有两种落点——「拒绝本次工具、对话继续」和「拒绝并中断整轮」，没有第三种。所以如果 `cancel` 不中止任务，它与 `deny` 的行为就完全一致，只剩「有没有填理由」的差别。

**请二选一：**

- **方案 A（我方推荐，零改动）**：`cancel` = 中止整轮任务，等价于 §6.3 的停止，只是入口在确认框上。
  - 文档改为：「`cancel`：中止整个任务，效果等同 §6.3 `task.cancel`」。
  - 前端约定：「×」/「关闭」按钮映射为 **`deny`**（只拦这一步），只有明确的「终止任务」按钮才发 `cancel`。
- **方案 B**：`cancel` = 只关掉这个框、不执行该操作、任务继续。
  - 那么它是 `deny` 的别名，我方把 `cancel` 也映射成 deny；中止任务只能走 `task.cancel`。
  - 文档需要说明 `cancel` 与 `deny` 的实际差异仅为语义标注。

两种我们都能支持（改动一行），但**必须先定下来**。

**顺带确认**：`deny` 的措辞「让被控子进程走『被拒』分支而不是失败」与我方实现一致——模型会收到拒绝理由并继续对话，任务照常走到 `task.completed`，`metadata.permission_denials` 里能查到被拒记录。

## ② §8.1 的 `confirm_required` 示例仍带 `"timeout": 60`（P1）

**v2 现状**（§8.1 示例）：

```json
"level": "dangerous",
"timeout": 60
```

**问题**：既然已定「**审批不设超时，确认框可以一直挂着等人**」，示例里留着这个字段，前端很可能照着实现成 60 秒倒计时自动关框——等于把我们刻意去掉的超时又加回来了，而且是以最糟糕的方式（静默失效，用户从手机上点进来时框已经没了）。

**建议**：删除示例中的 `timeout` 字段；若要保留字段定义，请加注：

> `timeout`（可选）：ywcoder shim **不发送**该字段。缺省表示无限等待，**前端不得自行设置默认超时或倒计时自动关闭**。

## ③ §6.3 的「较长任务超时（默认 5 分钟）」（P1）

**v2 现状**（§6.3 结尾）：

> 可另保留一个较长任务超时（默认 5 分钟，可配 `-task-timeout`）作为兜底。

**问题**：5 分钟不能称为「较长」，且与人工审批场景直接冲突——用户在手机上看到通知再点进来，十几分钟很正常。5 分钟兜底会把**正常的人工确认**当成挂死任务砍掉。

**建议**：默认值改为 **30 分钟**起（之前口头对齐的是 30~60 分钟），文档写成：

> 任务超时默认 30 分钟（可配 `-task-timeout`）。该值必须显著大于人工审批的合理等待时间，5 分钟级别的默认值会误杀正常确认。

## ④ `session_id` 的产生方与格式约束未写进文档（P1）

**v2 现状**：§6.1 示例里 `session_id` 直接给出，§12「会话与上下文」只解释了它的含义，**没写这个 id 由谁产生、要满足什么格式**。

**我方已适配现状**：AgentClient 目前在首条 `task.create` 就下发 UUID 格式的 `session_id`，我方**原样采用、不另生成**（已实测四个分支）；若某次不下发，我方 mint 一个 UUID 并在 ack 回传。两种入口都支持，**`task.create` 的 ack 里回传的 id 即权威 id**。

| 下发的 `session_id` | 我方行为 |
|---|---|
| 合法 UUID、本地无该会话 | 以该 id 新建会话（`--session-id`） |
| 合法 UUID、本地已有该会话（同工作目录） | **续接，恢复历史上下文**（`--resume`） |
| 合法 UUID、但工作目录变了 | 视为新会话（会话文件按工作目录分桶存） |
| 非 UUID（如 `{task_id}-session`） | 退化为**一次性会话，不可续接** |

**因此需要贵方保证三点**（这是把「保证 UUID」的责任交给下发方之后的必然要求）：

1. **必须是合法 UUID**（`8-4-4-4-12` hex）。非 UUID 会**静默丢失续接能力**——子进程回收后上下文即消失，用户表现为「聊着聊着失忆」。网关的 `{task_id}-session` 兜底值正是这种形态，请确认不会流到这一层。
2. **UUID 固定使用小写**。大写能正常启动，但会话文件名就是这个 id：macOS 文件系统大小写不敏感会「碰巧」命中，**Linux 上同一个 id 的大小写变体会被判成两个不同会话**（本该续接的变成新建）。跨平台行为不一致。
3. **`session_id` 与工作目录配套**。同一个 id 换了 `--workdir` 就是全新会话；若产品上允许一个会话中途切换工作目录，上下文会静默丢失。

**建议**：在 §6.1 或 §12 补一段：

> `session_id` 标识一次连续对话，可由 AgentClient 下发，也可由本地 Agent 在首条 `task.create` 的 `result` 中回传（此时 `task.create` 可不带该字段）；两种情况下都以 `result` 中的 id 为准。若由 AgentClient 生成，**必须是小写的合法 UUID**，且在该会话的整个生命周期内保持不变。
