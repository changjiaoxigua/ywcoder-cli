# 软件许可证（License）完整指南

## 一、定义

软件许可证（Software License）是一份法律文件，明确规定了软件的使用条款，包括：
- 谁可以使用该软件
- 可以做什么（使用、复制、修改、分发等）
- 必须遵守什么条件（保留版权声明、开源衍生作品等）
- 免责声明和责任限制

> **简单说**：许可证是作者对用户的"使用授权书"。

---

## 二、用途

| 用途 | 说明 |
|------|------|
| **保护作者权益** | 声明版权归属，防止他人盗用或侵权 |
| **明确用户权利** | 告诉用户可以做什么、不能做什么 |
| **法律免责** | 通过免责声明（AS IS）免除因软件使用造成的损失责任 |
| **促进传播** | 合适的许可证能让更多人放心使用 |

> **关键认知**：没有许可证 ≠ 自由使用。默认情况下，软件受版权法保护，"保留所有权利"（All Rights Reserved）。

---

## 三、由来

### 历史背景

| 时间 | 事件 |
|------|------|
| 1980s | 软件开始受版权法保护，专有软件盛行 |
| 1985 | 自由软件基金会（FSF）成立，推出 GPL 许可证 |
| 1988 | MIT 许可证诞生（最早的开源许可证之一） |
| 1998 | 开源促进会（OSI）成立，建立"开源定义" |
| 1999 | Apache 许可证 1.0 发布 |
| 2004 | Apache 许可证 2.0 发布（引入专利授权） |

### 核心概念

- **专有软件（Proprietary）**：保留所有权利，需单独授权
- **自由软件/开源软件（FOSS）**：授予用户自由使用、研究、分享和改进的权利

## 四、主流开源许可证对比

| 许可证 | 宽松度 | 来源 | 使用场景 | 使用方法 | OSI 认证 |
|--------|--------|------|----------|----------|---------|
| **MIT** | 🟢 最宽松 | 麻省理工学院 (1988) | 希望最大化传播，允许闭源商用 | 创建 LICENSE 文件，粘贴 MIT 文本，修改版权行 | ✅ 是 |
| **Apache 2.0** | 🟢 宽松 | Apache 软件基金会 (2004) | 企业项目，需要专利保护 | 同上，使用 Apache 2.0 模板 | ✅ 是 |
| **BSD 2-Clause** | 🟢 最宽松 | 加州大学伯克利分校 (1999) | 类似 MIT，条款更简洁 | 同上，使用 BSD 模板 | ✅ 是 |
| **BSD 3-Clause** | 🟢 宽松 | 加州大学伯克利分校 | 需要禁止用项目名背书 | 同上 | ✅ 是 |
| **GPL-2.0/3.0** | 🔴 严格 | 自由软件基金会 FSF | 强制衍生作品开源，保护自由软件生态 | 同上，注意传染性要求 | ✅ 是 |
| **LGPL** | 🟡 中等 | 自由软件基金会 FSF | 库文件使用，允许链接不传染 | 同上 | ✅ 是 |
| **MPL-2.0** | 🟡 中等 | Mozilla 基金会 | 文件级开源，平衡自由与商业 | 同上 | ✅ 是 |
| **CC0** | 🟢 放弃版权 | Creative Commons | 彻底放弃版权，奉献给公有领域 | 同上 | ✅ 是 |
| **专有软件** | ⚫ 无许可 | 各公司/个人 | 保留所有权利，需单独授权 | 写 Copyright 声明，不提供许可证 | ❌ N/A |

### 使用方法通用步骤

1. **选择许可证**：根据需求从上表选择
2. **创建文件**：在项目根目录创建 `LICENSE` 或 `LICENSE.txt`
3. **填写内容**：复制许可证模板，修改版权行（`Copyright (c) [年份] [你的名字]`）
4. **package.json**：添加 `"license": "MIT"`（或其他）
5. **代码头部**：可选，在源文件头部添加版权注释

> **注意**：都不需要向任何机构申请或认证，直接声明即可生效。

## 五、OSI 认证的关系

### OSI 是什么

**开源促进会**（Open Source Initiative）是一个非营利组织，成立于 1998 年，负责维护"开源定义"（Open Source Definition, OSD）。

### OSI 的作用

| 作用 | 说明 |
|------|------|
| **认证** | 审核许可证是否符合开源定义 |
| **列表** | 维护"OSI 批准许可证"列表 |
| **背书** | 为企业提供可信度参考 |

### 与许可证的关系

```
┌─────────────────────────────────────┐
│         许可证诞生                    │
│    （作者/组织自行创建）               │
└─────────────────────────────────────┘
                ↓
┌─────────────────────────────────────┐
│      提交给 OSI 审核                  │
│    （自愿行为，非强制）                │
└─────────────────────────────────────┘
                ↓
┌─────────────────────────────────────┐
│    OSI 认证通过 / 不通过               │
│   （通过后加入 OSI 批准列表）          │
└─────────────────────────────────────┘
```

### 关键认知

- **OSI 不是发布机构**：MIT、Apache、GPL 等许可证都先于 OSI 存在
- **OSI 不是审批机构**：你不用向他们申请才能使用这些许可证
- **认证 = 信誉背书**：通过 OSI 认证的许可证，企业更放心使用
- **非强制**：你可以用 OSI 认证的，也可以用其他的

### 类比

- **OSI** 像"米其林餐厅指南"
- **许可证** 像餐厅本身
- **关系**：米其林给餐厅打分认证，但餐厅不是米其林开的

## 七、潜在风险点

### 1. 版权侵权风险 ⚠️

**问题核心**：Anthropic 从未官方开源 Claude Code，源码流出属于未经授权的分发。

```
Anthropic 版权 → 未授权流出 → 被使用 → 潜在侵权
```

**可能后果**：
- 收到 DMCA 下架通知
- 被要求停止项目
- 极端情况：法律诉讼

**风险程度**：取决于 Anthropic 是否追究（很多公司选择不追究已广泛流出的代码）

### 2. 混合版权的复杂性

| 代码来源 | 许可证 | 风险 |
|----------|--------|------|
| Anthropic 原始代码 | 专有（未授权）| ⚠️ 无使用许可 |
| YwCoder 修改 | MIT | ✅ 合法声明 |

**问题**：
- 无法将 MIT 应用于整体项目（因为包含专有代码）
- 用户难以区分哪些部分可以用、哪些不可以用
- 企业用户可能因合规风险而放弃使用

### 3. 下游使用者风险

| 使用者 | 风险 |
|--------|------|
| **项目维护者** | 持续的法律不确定性 |
| **贡献者** | 为可能侵权的项目提交代码 |
| **最终用户** | 使用可能侵权的软件 |
| **企业用户** | 法务审查可能不通过 |

### 4. 改名风险（已解决）

将项目从 OpenClaude 改名为 YwCoder **不构成侵权**，因为：
- OpenClaude 本身也是衍生项目，不是独立版权所有者
- "OpenClaude" 不是注册商标
- 你的修改是你的创作，有权决定品牌名称

## 八、建议：考虑直接保留版权的原因

### 适用场景

如果 YwCoder **仅供公司内部使用**，建议：

**不采用 MIT 或其他开源许可证，直接保留版权声明**

```text
Copyright (c) 2026 [公司名]. All Rights Reserved.
仅供内部使用，未经授权不得对外分发。
```

### 理由

| 理由 | 说明 |
|------|------|
| **1. 无需开源合规** | 不涉及开源许可证的复杂合规要求 |
| **2. 保护商业机密** | 避免代码意外泄露后被自由使用 |
| **3. 简化法律风险** | 不涉及 Anthropic 代码的 MIT 授权争议 |
| **4. 明确归属** | 员工流动时明确代码归属，防止被带走开源 |
| **5. 无需 OSI 认证** | 内部使用不需要任何外部认证或审批 |
| **6. 成本最低** | 不需要法务审查开源许可证合规性 |

### 与开源方案的对比

| 维度 | 直接保留版权 | 采用 MIT（当前） |
|------|-------------|-----------------|
| **法律风险** | 低（内部使用，版权清晰） | 高（涉及 Anthropic 专有代码） |
| **对外传播** | 禁止 | 允许（但原始代码部分存疑） |
| **社区贡献** | 无 | 可能吸引贡献者 |
| **企业采用** | N/A | 可能因合规问题被拒绝 |
| **维护成本** | 低 | 高（需处理版权争议） |

### 结论

> **仅供内部使用 = 不需要开源许可证**
>
> 直接写 `Copyright (c) 2026 [公司名]. All Rights Reserved.` 即可，
> 不需要任何 OSI 认证，也不需要任何机构审批。
