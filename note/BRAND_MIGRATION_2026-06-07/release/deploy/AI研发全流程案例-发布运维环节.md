# AI 介入研发全流程实用案例 · 发布/运维环节
## 子题：内网离线部署脚本（安装 / 配置 / 更新 / 卸载）需求说明与 AI 协作成效总结

| 项 | 内容 |
|---|---|
| 场景 | ywcoder（去品牌化的 CLI 编码工具）内网离线部署 |
| 环节 | 研发全流程中的「发布 / 运维（DevOps）」环节 |
| 产出 | 3 个部署脚本 + 1 份使用说明 + 本案例文档 |
| 协作形式 | 工程师提出目标与约束，AI 负责分析、设计、编码、测试、查错、文档 |

---

## 一、背景与问题

工具完成品牌去标识后需在**内网、离线**环境分发给一线用户使用。初始的配置方式是一段把环境变量写进 `~/.bashrc` 的 shell 脚本，存在以下痛点：

1. **易错且静默失败**：脚本里把开关变量名误拼为 `YWCODEDR_USE_OPENAI`（多一个字母 D），导致 provider 根本没被激活、连不上网关，且无明显报错；模型名里混入了非 ASCII 连字符，网关无法识别。
2. **环境耦合**：配置写死在 `~/.bashrc`，只有 bash 生效、zsh 用户失效；改完要 `source` 或重开终端；多 rc 文件易遗漏。
3. **缺乏完整生命周期**：只有"配置"，没有统一的安装/更新/卸载/迁移方案；老用户从旧配置迁移、用户改网关/换 key、卸载还原都没有标准动作。
4. **使用门槛**：一线用户非技术背景，手动填 key/地址/包名、记命令，门槛高。

---

## 二、需求说明

### 2.1 目标
用尽量少的用户操作，完成内网工具的**安装、配置、更新、修改配置、卸载**全生命周期，并让**存量用户平滑迁移**到新配置方式，降低出错率与操作门槛。

### 2.2 功能需求（FR）

| 编号 | 需求 |
|---|---|
| FR-1 | **离线安装/更新**：从本地 `.tgz` 包安装（`npm install -g ./包名`），不依赖外网 registry |
| FR-2 | **配置写入**：provider 配置（开关 / key / 网关地址 / 模型）写入应用配置文件 `~/.ywcoder/settings.json` |
| FR-3 | **首配交互、之后复用**：首次运行交互式询问 key/网关；之后再运行自动复用已有配置、不再询问 |
| FR-4 | **存量用户迁移**：自动识别老用户在环境变量里的旧配置，迁移进 settings.json，并清理旧的 shell 残留（含历史 typo 变量名） |
| FR-5 | **修改配置**：提供"重新配置（换网关/轮换 key）"入口，且不误改其它项（如模型） |
| FR-6 | **卸载/还原**：卸载程序 + 清理配置目录 + 清理 shell 残留，回到干净状态 |
| FR-7 | **安装自检**：装完自动连一次网关验证连通性 |

### 2.3 非功能需求（NFR）

| 编号 | 需求 |
|---|---|
| NFR-1 | **跨 shell**：bash / zsh 均生效，重开终端即生效，不污染用户 rc 文件 |
| NFR-2 | **健壮性**：误用 `sh` 运行不报错；缺少 `jq` 时自动降级；包不存在/未安装等异常不致命中断 |
| NFR-3 | **幂等可重复**：脚本可反复运行，不产生副作用堆积 |
| NFR-4 | **安全**：配置文件含密钥，权限收紧（`chmod 600`） |
| NFR-5 | **低依赖**：仅依赖目标机常见组件（Node/npm/bash），`jq` 可选 |
| NFR-6 | **去品牌一致**：全程使用新变量名 `YWCODER_*`，旧名只清不写 |

### 2.4 约束
内网无外网、离线分发；目标平台 Linux；包名由管理员每次手动指定（离线包文件名）；不暴露原品牌信息。

## 三、方案设计与关键技术决策（AI 协作产出）

AI 的价值不只在"写脚本"，更在于**基于真实源码核验后再决策**，避免拍脑袋。关键决策与依据：

| 决策点 | 结论 | AI 给出的依据（源码核验） |
|---|---|---|
| 配置载体：`.bashrc` 还是 `settings.json`？ | **选 settings.json** | 核验 `managedEnv.ts` 确认应用启动时会把 settings.json 的 `env` 注入进程；跨 shell、免 source、不污染 rc |
| settings.json 能否通过首启的强制校验？ | **能**（先经真机验证再定方案） | 分析启动时序（`cli.tsx` 校验 vs env 注入顺序），识别出潜在时序风险点，**要求内网先验证**，实测通过后才据此定方案 |
| 老用户配置怎么迁移？ | **脚本自动读当前 shell 环境变量**写入 settings.json | 利用"子进程继承父 shell 已 export 变量"的机制，老用户零重输 |
| 未配置时为何暴露原品牌？如何兜底？ | 根因=默认回退 firstParty；建议用 **managed/policy settings** 兜底 | 定位 `providerConfig.ts` 默认返回 `firstParty`、核验 policy settings 优先级与路径 |
| 改配置怎么做？ | `--reconfigure`（重问 key/网关，**保留模型**）/ 直接编辑 / 环境变量传参 | —— |

## 五、AI 介入的提升效果（总结）

### 5.1 过程对比

| 维度 | 传统方式 | 本次 AI 协作 |
|---|---|---|
| 方案选型 | 凭经验/试错，常需多轮返工 | 先读源码核验机制 → 给出有依据的方案，必要处用真机验证再定 |
| 编码 | 手写、易漏边界 | 一次性产出含异常处理、降级、幂等的脚本 |
| 查错 | 多在用户现场暴露 | 多数缺陷在编码/测试阶段前置拦截 |
| 文档 | 常滞后或缺失 | 与代码同步产出 README + 案例 |
| 周期 | 通常数天、跨多次沟通 | 同一会话内完成"分析→实现→测试→文档"闭环 |

### 5.2 具体收益（本案例实际发生）

**① 缺陷前置拦截**——在交付/上线前发现并修复了多处真实缺陷：
- 原脚本变量名 typo `YWCODEDR_USE_OPENAI` → 会导致**连不上网关且无报错**；
- 模型名非 ASCII 连字符 → 网关识别失败；
- `sh` 运行触发 `pipefail` 报错 → 加自动切 bash 的保险；
- **脚本自身 `OPENAI_MODEL` 变量名与环境变量同名冲突**，导致老用户模型迁移失效——此 bug 是 AI 通过**构造隔离测试用例**发现的，而非等到现场；
- `setup-new.sh` 的网关地址缺"占位则询问"保护 → 可能静默连到无效地址，补齐。

**② 决策有据，减少返工**：配置载体、启动时序、品牌兜底等关键问题，均**基于实际代码核验**得出结论（而非猜测），并在拿不准处主动要求"内网先验证再定方案"。

**③ 边界覆盖更全**：一次性覆盖 sh/bash 兼容、离线无 registry、jq 缺失降级（jq→python3→整写）、新/老/全新三类用户、密钥特殊字符、密钥文件权限、卸载非致命等边界。

**④ 知识传递**：对非专业概念（rc 文件、`source`、`jq`、npm 全局安装与 HOME 配置的区别、为何 `npm uninstall` 不清配置目录）做了通俗解释，沉淀为团队可复用认知。

**⑤ 生命周期完整**：从"只有一段配置脚本"扩展为"安装/配置/迁移/改配置/更新/卸载"的完整运维工具链 + 文档。

### 5.3 AI 在本环节的角色定位
**不是替代工程师做决定，而是充当"懂代码的高速执行+核验助手"**：工程师把控目标、约束与验收（尤其真机验证由人把关），AI 负责把"分析—设计—编码—自测—查错—文档"压缩到一个连续会话内完成，并主动暴露风险点交人决策。

## 六、可复用的方法论 / 亮点

1. **先核验、后断言**：涉及运行时行为的判断，AI 先读源码/查机制再下结论，拿不准就让人真机验证——避免"看起来对"的方案上线翻车。
2. **隔离测试抓隐性 bug**：对脚本里取值优先级这类逻辑，单独构造最小测试用例验证，提前抓出变量名冲突等隐性缺陷。
3. **健壮性默认内建**：异常不致命、依赖可降级、运行方式容错、操作幂等——按"会被各种姿势使用"来设计。
4. **配置与程序解耦**：配置落应用自有目录（HOME），更新/卸载程序不影响配置——降低运维心智负担。
5. **面向非技术用户做减法**：交互最小化（首配问一次、之后复用、老用户自动迁移），并配套通俗文档。
